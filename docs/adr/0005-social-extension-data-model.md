# ADR-0005: ソーシャル拡張(他人の本機能)のデータモデル方針

- ステータス: 採用
- 日付: 2026-05-14 起票 / 2026-05-15 D7.1 を「暗黙ルール案」に修正 / 2026-05-19 D7.1 確定(案A 採用)
- 関係者: makimaki
- 注: ADR-0004 は Supabase Data API GRANT 規約用に予約済み(2026-05-15 Week 2 振り返り時に起票予定)

## コンテキスト

### 背景

StoryMapper のα版は「読書中の中断問題を自分のメモで解決できるか」というコア仮説を検証する範囲に絞っている (memo: α版スコープ確定 2026-04-28)。

一方、β以降には以下のソーシャル拡張を計画している:

1. 他人の読書まとめ(StoryMapper 上の本)を**参考閲覧**できるビューアー (`/bookreview/{id}`)
2. main 画面に「参考にしている他人の本」リストを表示する
3. 公開された他人の本を探索・購読する画面 (`/select`)
4. (長期) 読書行動メタデータの収集と、入力者への還元設計

これらは 2026-05-14 に作成した画面遷移案 v1 (PDF) で枠として描かれた。

### 課題

α版実装段階でデータモデル v1 を確定し migration を本番適用済みである。
β拡張時に **既存カラムの削除・型変更・既存 RLS policy の削除など破壊的変更**が発生すると:

- 運用中のα版データに影響する
- ロールバック・データ移行の負担が増える
- α版実装中に「これは β でこう変わる予定」という暗黙の前提を抱え続けることになり、設計の汚染が起きやすい

そのため、データモデル v1 が「他人の本」概念を**後付けで非破壊的に**追加できる構造であることを今のうちに確認・宣言する。確認するだけで、α版実装に向けて今すぐ v1 を変更する必要はない。

### 対象範囲

本 ADR は以下のみを扱う:

- β拡張時のデータモデル方針の確定
- α版実装に影響を与えないことの確認
- β実装時の migration の青写真

以下は**対象外** (別 ADR または β実装着手時に決定する):

- 公開操作の UI 仕様 (公開可否トグル、公開範囲、解除フロー)
- 推薦・検索アルゴリズム
- メタデータ収集と還元の具体的設計
- マネタイズ戦略との関係
- モデレーション・通報

## 決定

### D1. α版実装ではデータモデル v1 を維持する

他人の本機能はα版では実装しない。α版実装期間中はデータモデル v1 を一切変更しない。

α版の main 画面に「他人の本リスト」枠を**スケルトン表示**として残すかは UX 判断 (別議論)。
残す場合もデータソースは存在しない (常に空) という扱いとし、データモデルには影響させない。

### D2. β拡張は非破壊的な追加のみで実現する

β拡張時には以下の3種の変更のみで対応する:

- `ALTER TABLE` で既存テーブルにカラム追加 (NOT NULL は DEFAULT 付き)
- `CREATE TABLE` で新規テーブル追加
- `CREATE POLICY` で RLS policy 追加 (既存 policy は変更しない)

**既存カラムの削除・型変更・既存 policy の削除は行わない**。

### D3. 「自分の本」「他人の本」の区別は books.user_id ベースで一貫させる

シーン (scenes) ・ メモ (memos) ・ キャラ (characters) ・ 状態履歴 (character_states) 等は books に外部キーで連鎖する。所有判定は常に `books.user_id` を起点に行い、子テーブルに重複した所有情報は持たない。

これにより、α版実装中も β拡張後も「データ所有の真実の源 (single source of truth)」は books.user_id 1箇所に保たれる。

### D4. β拡張時に追加する構造 (青写真)

#### D4.1 books.is_public フラグ

```sql
ALTER TABLE books ADD COLUMN is_public BOOLEAN NOT NULL DEFAULT false;
```

- α版から作成された既存本はデフォルト非公開
- 本人が明示的に公開操作した時のみ `true` に更新される
- 公開の取消も同カラムで管理 (true → false)

#### D4.2 book_subscriptions テーブル

```sql
CREATE TABLE book_subscriptions (
  user_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  book_id UUID NOT NULL REFERENCES books(id) ON DELETE CASCADE,
  added_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, book_id)
);
ALTER TABLE book_subscriptions ENABLE ROW LEVEL SECURITY;

CREATE POLICY "users_manage_own_subscriptions" ON book_subscriptions
  FOR ALL TO authenticated
  USING (user_id = auth.uid())
  WITH CHECK (user_id = auth.uid());
```

- 「自分が参考にしたい他人の本」を表現する関連テーブル
- main 画面の「他人の本リスト」のデータソース
- 自分のレコードのみ操作可能 (本人による購読管理)

GRANT 文は ADR-0004 (起票予定) で規約化される内容に従う。

#### D4.3 公開本への閲覧 policy 追加

```sql
-- books
CREATE POLICY "public_books_readable_by_subscribers" ON books
  FOR SELECT TO authenticated
  USING (
    is_public = true
    AND EXISTS (
      SELECT 1 FROM book_subscriptions
      WHERE user_id = auth.uid() AND book_id = books.id
    )
  );
```

memos / scenes / character_states / labels / scene_labels にも同等の policy を追加する。
具体的な条件 (例えば「下書きメモは公開しない」等) は β実装時に決定。

#### D4.4 既存ビューへの影響

`visible_scenes` / `visible_memos` / `latest_visible_character_states` / `visible_characters` 等の既存ビューは `security_invoker = true` (ADR-0003) で評価されるため、上記 D4.3 の policy 追加だけで他人の本に対しても自動的に正しく動作する。ビュー定義の変更は不要。

### D5. 他人本に対するネタバレフィルタの扱い (β実装時に決定)

**本 D5 が扱う範囲は「他人本のフィルタ仕様」のみに限定する**。
自分本のネタバレフィルタは α版実装フェーズの最優先論点として別途設計ノートで詰める
(参照: `storymapper_self_book_spoiler_filter_notes.md` — α版実装着手前に整理を完了させる前提)。

他人の本を閲覧する際、誰の `current_scene_id` でフィルタするかは未確定。

検討中の案:

- 案 α: 閲覧者自身に「他人の本に対する自分の進捗」を持たせ、それでフィルタ → reading_progress を他人本にも書く運用に拡張
- 案 β: 公開者側の current_scene_id でフィルタ → プライバシー懸念
- 案 γ: フィルタ無効化 → ネタバレを気にせず読む (「参考」用途として明示)

β実装時に決定する。

**重要**: どの案を採用しても、データモデル v1 への ALTER のみで対応可能であることを確認済み。

- 案 α: reading_progress テーブルへのカラム追加 (`subscribed_book_id` 等) または policy 拡張で対応
- 案 β: 新規ビュー追加 (`subscribed_books_with_public_progress` 等) で対応
- 案 γ: 追加変更不要

つまり本 ADR の D2 (非破壊原則) はネタバレフィルタ仕様にも適合する。

なお、自分本フィルタが既存ビュー (`visible_scenes` / `visible_memos` 等) で実装されることから、他人本フィルタは **同じビュー定義に閲覧者 policy が追加される形で自動的に効く**(ADR-0003 の security_invoker 効果)。すなわち β拡張時にビュー定義を書き直す必要はない。

### D6. メタデータ収集と還元 (長期構想)

「読書行動メタデータの収集と入力者への還元」は本 ADR の対象外。

ただし、収集対象データが何になるにせよ、起点となるのは books / memos / character_states / reading_progress 等の既存テーブルである。新規の集計テーブルや分析用スキーマを追加する形で対応可能 (CREATE TABLE 範囲)。本 ADR の非破壊原則と矛盾しない。

具体設計は別 ADR (β中盤以降の起票) で扱う。

### D7. α版実装時に意識する事項 (β拡張への布石)

α版実装中、**新規カラムやテーブルを追加せずに**「将来の公開対象 / 非公開対象の分類」を意識した設計を行う。フラグ追加は β拡張時に ALTER で実施するが、α版時点では UI 設計・コード設計・ドキュメントレベルで分類を意識する。

#### D7.1 メモのライフサイクル設計 — 採用案: 案A(本文必須ブックマーク)

> **ステータス: 確定(2026-05-19, Week 3 Day 4)**
> 2026-05-15 (Day 7) に画面遷移マップ v1 §3.3.1 との矛盾を発見し「暗黙ルール案」として保留していたが、2026-05-19 (Week 3 Day 4) の議論で案A/B/C を検討し**案A を採用**。

**採用ライフサイクル(案A):**

```
[ワンタップ] ブックマーク作成 UI(本文必須、空欄送信不可)
   ↓ 同一フォーム内で本文入力
本文ありブックマーク (is_bookmark=true, bookmark_note=有)
   または
通常メモ (is_bookmark=false, 本文有)
```

**α版での「本文空ブックマーク」は構造的に存在させない** ことで、画面遷移マップ v1 §3.3.1「ワンタップ + 本文同時入力UI」と整合させる。

**β拡張時の公開対象判定:**

α版時点で「本文空ブックマーク」が存在しないため、当初想定の `WHERE bookmark_note IS NOT NULL OR is_bookmark = false` による暗黙シグナル方式は機能しない。代わりに **新規フラグ追加**で対応する:

```sql
ALTER TABLE memos ADD COLUMN is_public_eligible BOOLEAN NOT NULL DEFAULT true;
```

または別アプローチ(タグ、メモタイプ等)を β拡張時の UI 仕様に合わせて選択。フラグ追加は本ADRの D2(非破壊原則)とは整合する(`ALTER TABLE ADD COLUMN` のみ)。

**理由(案A 採用の決め手):**

1. **α版コア仮説の優先順位**: 2026-05-19 議論で Makimaki が「整理価値メインに振る」「空ブックマーク自体の検証に現段階で価値を置いていない」と確定。コア仮説「読書中断族の整理ニーズ」に集中するため、ブックマーク UX の検証は α版範囲から外す
2. **実装スコープの単純化**: 案B/C で必要となる「後続編集UI(整理画面 or インライン編集)」を α版から外せる
3. **β拡張時の判断負荷低減**: 暗黙シグナルより明示フラグの方がユーザーが理解しやすい(「これは公開していい? ダメ?」の判断に明示シグナルが効く)
4. **D7 全体思想の維持**: D7.1 のみ局所緩和であり、D2(非破壊原則)・D3(books.user_id 一元化)・D4(青写真)・D7.2(キャラ公開対象分類)は維持される

**α版の「整理価値」提供方針(関連):**

独立した整理画面は α版に作らない。`/books/{id}` reading 画面で以下を一画面に集約することで整理価値を提供する:

- 現在シーン情報 + chapter ラベル名
- メモ一覧(本文あり)+ ブックマーク一覧(本文あり)
- キャラ即参照
- シーン履歴(進行・後退)

独立した整理画面・サマリー画面は β以降に持ち越し。α版ユーザー検証で「`/books/{id}` だけで整理価値が伝わるか」のフィードバックを集め、β以降の整理画面設計の最重要インプットとする。

**「ブックマーク」と「通常メモ」の差(α版):**

両者とも本文必須なので、データ上は `is_bookmark` フラグの true/false で区別するのみ。UI 上の作成導線・表示の違いは画面遷移マップ v1 §3.3.1 とメモ+ブックマーク UI 実装(Week 3 Day 5-7)で詳細を詰める。

**検討した代替案(2026-05-19 議論):**

- **案B: 暗黙ルール維持 + 画面遷移マップ §3.3.1 を Day 6 当初想定に戻す**
  - ブックマーク UI = ワンタップで本文空ブックマーク作成、本文記入は別画面(整理画面 or インライン編集)で後から
  - メリット: D7.1 当初想定の暗黙シグナルでβ拡張時に新規フラグ不要、「読書中の思考が走った瞬間にワンタップ」体験を確保
  - 不採用理由: 「本文空ブックマーク」が大量に残った場合の整理画面の必要性が α版スコープを侵食する懸念。Makimaki が「空ブックマーク自体の検証に現段階で価値を置いていない」と表明
- **案C: 両立 — 本文同時入力UIを出すが空欄送信OK(2ボタンUI)**
  - ボタン2つ: 「あとで書く」(本文空のまま保存)/「保存」(本文ありで保存)
  - メリット: 暗黙シグナル維持と画面遷移マップ整合の両立、ユーザーに明示選択肢を与える
  - 不採用理由: UI 複雑化、ユーザー選択判断の負担増。「あとで書く」を採った後の後続編集UI(整理画面 or インライン)が α版に必要となり、案B と同じくスコープ侵食懸念

#### D7.2 キャラ・キャラ状態の公開対象分類

キャラ・キャラ状態についても同様の議論を α版実装フェーズで詰める:

- 公開対象 = キャラ名・初登場シーン・基本属性
- 非公開対象候補 = 個人的な感想・解釈メモ(別途 memos に書く想定?)
- α版実装時に「キャラの何が公開対象になりうるか」を意識した設計を行う

**理由 (D7 全体)**: 「作りこんでから隠す」コストは「最初から意識する」コストよりはるかに大きい。特にメモ単位の分類変更はデータ移行が発生するため致命的。

## 結果 (Consequences)

### ポジティブ

- α版実装中に「他人の本機能の前提」を無自覚に壊すリスクを構造的に防げる
- β拡張時の migration 範囲が事前に明確化され、見積もり精度が上がる
- データ所有の真実の源が books.user_id 1箇所に集約され、設計の一貫性が保たれる
- ADR-0003 (security_invoker 必須) との組み合わせで、β拡張時のビュー所有問題が再発しない
- 画面遷移マップ v1 (2026-05-14) の構造を維持したまま、α/β の段階移行が可能

### ネガティブ

- α版時点で「使わない設計」を文書化するため、確認・更新の手間が発生する
- β実装着手時にも本 ADR を再確認する必要があり、設計判断が分散する
  → β着手時に本 ADR を更新する (ステータス: 採用 / 実装中 / 完了) ことで補う
- 「他人の本機能を一切実装しない」期間が長引くと、本 ADR の前提が陳腐化する可能性
  → Phase 2 移行判断時 (2026-10 想定) に再評価する
- D7.1 が案A 採用により、当初想定の「暗黙シグナルで新規フラグ不要」原則が一部緩和される
  → β拡張時に `memos.is_public_eligible` 等の新規フラグ追加が必要になる(ALTER TABLE ADD COLUMN のみで D2 非破壊原則とは整合)

## 検討した代替案

### A. α版から books.is_public カラムを入れておく

α版から非破壊原則を担保するため、is_public カラムだけ先に追加する案。

不採用。理由:

- α版で使用しないカラムを本番スキーマに残すと、運用時に「これは何のためのカラムか」を再認識するコストが発生する
- 公開機能仕様 (公開範囲、解除、モデレーション等) が未確定の段階でカラムを切ると、後で要件が固まった時に追加 ALTER が結局必要になる可能性
- β拡張時にまとめて ALTER した方が境界が明確で、ADR・migration の対応関係も追いやすい

### B. books テーブルをスキーマ分離 (`public_books` スキーマに分離)

公開本を別スキーマ・別テーブルに物理分離する案。

不採用。理由:

- 「自分の本を後から公開する」「公開を取り消す」操作で物理的にテーブル間移動が必要になる
- 参照整合性 (scenes / memos / characters 等の外部キー) の維持コストが過大
- 「自分の本」「他人の本」の境界が物理スキーマに固定されると、将来「友人限定公開」「リンク知ってる人のみ」等の中間状態を追加できない

### C. book_subscriptions ではなく books に subscribers JSONB

購読者リストを books に JSONB カラムで持つ案。

不採用。理由:

- 多数の購読者が付くと書き込み競合 (同一行の UPDATE 集中) が発生する
- RLS policy が JSONB 内検索 (`auth.uid()::text = ANY(subscribers->'user_ids')`) になり、性能・可読性ともに劣化
- 監査・削除・期間集計など「購読関係」を1レコードとして扱える方が拡張性が高い

### D. ソーシャル要素を Phase 1 終了時 (2026-07 末) のα版完成と同時に組み込む

α版に最初からソーシャル要素を入れて、検証範囲を広げる案。

不採用 (現時点)。理由:

- α版のコア仮説 (中断問題の解決) とソーシャル仮説 (他人のまとめが役立つか) を混ぜると、検証結果の解釈が困難になる
- 「公開者がいない状態では機能として成立しない」初期コールドスタート問題が未解決
- ただし Phase 2 開始時 (2026-08) にこの判断を再評価する余地は残す

### E. 都度判断 (規約化しない)

β実装時にデータモデル v1 への影響をその場で考える。

不採用。理由:

- α版実装が進むほどデータモデル v1 への暗黙の前提が増え、β拡張時に「ここは破壊的に変えるしかない」箇所が出るリスクが高まる
- 事前確認のコストは低く、確認しないコストの方が大きい

## 再評価判断基準 (Phase 2 開始時 = 2026-08 想定)

代替案 D で保留した「ソーシャル要素のα版組み込み」は Phase 2 開始時に再評価する。
以下を判断材料とする (チェックリスト形式):

- α版完走時 (2026-07末) のアクティブユーザー数 (自分以外 + α版テスター何名か)
- 「他人のまとめを見たい」「自分のを公開したい」という声の有無 (α版テスター/フィードバック経由)
- 自分自身のメモ蓄積 (Phase 2 開始時点で**自分自身が「公開していいレベルのメモ」を持っているか**) — 公開者ゼロ問題への現実的対策
- 競合状況 (Readwise / Notion 系のソーシャル機能動向)
- Phase 2 のリソース余力 (AI 整理支援機能とソーシャル拡張のどちらが優先か)

判断結果は Phase 2 着手時の追加 ADR (0006以降) で明文化する。
