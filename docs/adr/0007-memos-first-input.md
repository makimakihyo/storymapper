
# ADR-0007: memos-first 入力モデル（自由文＋AI抽出ハイブリッド）

- Status: **Accepted**
- Date: 2026-06-29（Proposed: 2026-06-25 / standalone 検証 2026-06-25・過剰抽出 eval 2026-06-26）
- 関連: ADR-0001（AI情報源制限）/ ADR-0006（character_states UPSERT）

## Context

character_states の状態記録を、ユーザーが location/goal/affiliation を**手で構造化入力する**形にしていた。実利用で出た不満（Week8 Day1-4 の10点）の根は「構造化入力の強制」。一方で、構造そのものは**キャラ動向のグラフ化**に必要なので捨てられない。問題は**入力方法**であって構造の有無ではない、と切り分けた（2026-06-22 決定）。

加えて、UI の根幹要件として「状態の閲覧・入力でページ遷移しない」（遷移した瞬間に文脈を忘れる、を避ける）が確定している。

## Decision

入力を**ハイブリッド**にする。

1. **同定・紐付けは明示構造のまま**: シーンに登場するキャラはユーザーが選択（既存から選ぶ／新規）。状態メモは (シーン × キャラ) に紐づけて入力。→ AI は「誰の・どのシーンの状態か」を推定しない。
2. **状態メモは自由文＋AI抽出**: ユーザーは自由文で書く。AI が `current_location / goal / affiliation` を抽出して `character_states` に格納する。
3. **スキーマは据え置き＋1カラム追加**:
   - `character_states`（per シーン×キャラ）: `current_location` / `goal` / `affiliation`（全て per-scene。**所属もシーンで変化する**）＝AI抽出の構造フィールド＝グラフ化の軌跡。
   - **`raw_memo` を追加**＝入力された自由文そのまま。**canonical（正）**。
   - `character`（本を通した情報・手入力）: 名前 / 別名 / 説明。
4. **抽出は tool-use（function calling）で構造強制**: `input_schema` でフィールドと型を縛る。プロンプト依頼で JSON が壊れる事故を構造で消す。
5. **raw_memo が正、抽出3欄は派生・助言的・ユーザー修正可**: 抽出結果は `character-state-form` に **prefill** し、ユーザーがレビュー/修正して確定（抽出は自動、確定は人間）。抽出が間違っても raw を見て直せる＝忠実性の安全弁。
6. **既存フォームに乗せる（再実装しない）**: 改修は `character-state-form` の prefill 供給源を〈現在シーンの既存record〉から〈AI抽出〉に**差し替えるだけ**。手戻り最小。
7. **抽出スコープ＝付与キャラのみ（v1）**: メモが他キャラに言及しても、状態を生やすのは紐づけたキャラだけ。横断生成はβ。
8. **自由文欄に例示プレースホルダ**（ソフトスキーマ）: 「例: 今どこにいるか／何を目指しているか／どの勢力と関わっているか／このシーンで起きたこと」。強制せず書き方を誘導＝抽出 recall も上がる。
9. **「そのシーンで起きたこと」は独立カラムにしない**: raw_memo に内包し、要約が拾う。イベントの構造化グラフが要るならβで列追加。
10. **抽出のフィールド別 厳格度**: `affiliation`・`current_location`＝**厳格**（このメモに明示が無ければ空。誤所属＝データ汚染なので空が正）。`goal`＝**軽い推測を許容**（目的はシーンをまたいで持続しがちで、毎メモでの再記述は非現実的）。いずれも raw_memo が正・ユーザーが確定するため、推測は prefill の便宜であって真実ではない。
11. **affiliation の格納正規化**: 抽出時に括弧類（`『』「」`）と前後空白を strip して格納＝グラフ化キーの一致を担保（Haiku `『組合』`／Sonnet `組合` のような表記揺れを吸収）。raw_memo は無加工で保持。

## 抽出モデルと品質（2026-06-26 確定）

- **抽出モデル＝Haiku 既定で確定**。standalone の過剰抽出 eval で両モデル 10/10 PASS＝忠実性は affiliation/current_location とも同等。差は goal の冗長度のみ（Haiku が簡潔）。
- コスト比は約2.4倍（単価比3.3倍ほど開かないのは Haiku が日本語で多くトークンを食うため）。**戒め: コスト試算は各モデルの実トークンで**。
- goal は冗長になりがち→プロンプトで「名詞句で短く」を指示。

## 責務分界（重要・混ぜない）

- **抽出**＝自由文→構造。扱うのは「ユーザーが今書いたメモ」＝既読範囲のみ。**抽出時点でネタバレ漏洩は構造的に起きない**。
- **ネタバレ防御**＝要約 / retrieve 側の責務。`scene <= current` の決定的フィルタ＋オフライン eval（ADR-0001 系）。
- → memos-first でこの2レイヤを混線させない。

## 要約の stale / 再生成（content-fingerprint 方式）

- 「シーンNまでの要約」はDB保存。**保存時に source 指紋を持つ**: 生成元（scene ≤ N の character_states ＋ シーン状況テキスト）の **max(updated_at)** と **行数**。
- **stale 判定（描画時計算・トリガー不要）**: 現在の source の max(updated_at) が保存値より新しい、**または**行数が違えば stale。max(updated_at)＝編集を捕捉 / 行数＝挿入・削除を捕捉。
- **「古い可能性あり」バッジ＝再生成のゲート**: バッジが無い（not stale）と再生成不可＝唯一の制限。
- 効果: **変わっていない成果物の再生成に課金しない**をデータで保証＝コスト規律。
- 注: `character_states.updated_at` は既存トリガ `trg_character_states_updated` で担保済み（本ADRで追加不要）。

## UX 原則（根幹）

- 状態・キャラ詳細の**閲覧/入力でページ遷移しない**: アコーディオン／インライン編集／ボトムシート＋ Server Action で遷移せず mutation。
- **データ先読み＋視覚マスク**: 1シーンのデータ量は小さい。タップ展開は取得済みデータの表示/非表示（lazy-fetch ではない）。
- **シーン変更時のみページ遷移**は可。

## Consequences

**Pros**
- 入力の心理的負荷を下げつつ、グラフ化に必要な構造を維持。
- 既存フォーム/スキーマをほぼ流用＝改修が小さく、退職後の限られた時間に収まる。
- 抽出は助言・人間が確定＝忠実性リスクに安全弁。
- 要約コストを構造的に規律＝運営（operation）の証跡を一段強化。

**Cons / Risks**
- 抽出の**忠実性**（メモに無い属性を創作しない）は要・継続 eval（過剰抽出 eval を本番門番化＝Week9 Day4）。
- coreference（誰の状態か）は UI の明示選択で回避済みだが、**メモ内の他キャラ言及**は v1 では取りこぼす（β）。
- raw_memo 追加＝1マイグレーション。既存 character_states 行は raw_memo NULL 許容で移行。

## Alternatives（却下）

- **全文自由文（シーン・キャラも文章から推定）**: coreference が最大の地雷でデータ汚染リスク。UI で同定を確定する方が安全＝却下。
- **構造強制を継続**: 不満10点の根そのもの＝却下。

## β送り

「起きたこと」の構造化グラフ／メモ内 他キャラ state 生成／章概念／複数本横断／ハード削除。
